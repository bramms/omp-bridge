# Опис проєкту та архітектура

## Мета й межі

Забезпечити пряме використання підтверджених zero-cost маршрутів OpenCode
зі штатного OMP, без запуску іншого агента. Розв’язати досліджену проблему
форми запиту та захистити від випадкової підміни безкоштовного SKU платним.
Не реалізовувати оркестратор, білінговий сервіс, SDK моделей, OAuth-брокер,
універсальний proxy framework або автоматичний ремонт акаунта.

## Компоненти

| Компонент | Відповідальність |
|---|---|
| `bridge.py` | CLI, локальний HTTP, discovery, free-only перевірка, TLS upstream, SSE і відмови |
| `extension.mjs` | Реєстрація провайдерів у OMP, підстановка session ID, команди каталогу |
| `tests/` | Перевірка логіки, локального HTTP та контракту extension API |
| `deploy/` | systemd user unit, необов'язкові WARP-вузли та короткий лаунчер |
| `evidence/sources.json` | Індекс джерел дослідження з датами й призначенням |

Два runtime-файли, стандартна бібліотека Python та API вже встановленого OMP.
Немає сторонніх Python/JavaScript залежностей, БД, обов'язкових контейнерів, глобального
перехоплення `fetch`, патчів `node_modules`, fork-build або власного agent loop.

## Шлях одного запиту

OMP будує власний запит, включно з історією, reasoning, схемами інструментів
і зображеннями. Локальний проксі перевіряє Host/Origin/token, розмір JSON,
точний lane/ID/endpoint і непрострочену zero-cost перевірку. Потім забирає
приватні поля `_omp_free_bridge` та `_omp_free_session`.

У звичайному режимі ідентифікує себе як `omp-free-bridge/<версія>`.
У явному compat-режимі формує OpenCode-подібні User-Agent/session і додає відсутні
назви інструментів: шість для Zen, п’ять для Go. Zen вирушає без API-ключа;
Go отримує ключ тільки після локальних перевірок. Далі відбувається один HTTPS
POST на фіксований хост OpenCode.

Звичайний `serve` читає від одного до десяти HTTP CONNECT-виходів Zen з
`STATE/zen-proxies.json`; повторювана `--zen-proxy http://HOST:PORT` перевизначає
файл. Відсутній файл або `[]` лишає прямий режим; зламаний файл блокує запуск.
TLS встановлюється до `opencode.ai` із перевіркою його сертифіката.
Go та discovery залишаються прямими.

Zen вибирає перший доступний маршрут у строгому порядку direct → WARP 1 → … →
WARP 10. Порядок не залежить від ID сесії. Відомі квотні та транспортні паузи
пропускаються; після відновлення прямого маршруту він знову має пріоритет.

`429 FreeUsageLimitError` до початку SSE ставить на паузу лише відповідний
маршрут за повним `Retry-After`, закриває його з'єднання та дозволяє наступну
спробу того самого POST. Тіло запиту й канонічна сесія готуються один раз.
Перед кожною спробою знову перевіряються allowlist моделі й зупинка каналу;
множина `attempted` обмежує кожен маршрут однією спробою. Для десяти WARP
максимум — одинадцять POST разом із direct. Відмови маршрутів незалежні в локальному
обліку. 401/402/403 зупиняють канал. Вибір маршруту та паузи захищені lock;
мережеві операції працюють поза ним.

`/health` показує пряму квоту, десять WARP-слотів, IP-спостереження й дублікати.
`X-OMP-Zen-Route: direct|warp` вказує маршрут відповіді; `X-OMP-Zen-Proxy` —
номер WARP-слота. `zen-cooldowns.json` schema 2 зберігає `quotas` окремо від `transport`.
Необов'язковий `last_429` зберігає за адресою маршруту час отримання відмови,
точний заголовок `Retry-After`, тип помилки й застосований дедлайн.
Отримання HTTP 429 записується до читання тіла; помилка читання не губить
заголовок. Стара schema 1/2 без історії зберігає дедлайни з невідомими деталями.
Історія лишається після зміни IP й закінчення паузи; `/health` відділяє її від
точного кінця чинної квотної чи транспортної паузи. `doctor` показує ці дані
окремою таблицею з UTC-зсувом і позначками невідомих значень.
Ключ `direct` і ключі адрес проксі мають незалежні квотні дедлайни. Старий
`direct_until` із schema 1 переноситься тільки в direct, старі proxy-паузи —
до відповідних маршрутів. Перезапуск і перестановка слотів зберігають дедлайни.
Окремий монітор раз на 60 с робить GET `/cdn-cgi/trace` через прямий маршрут
та кожен CONNECT, перевіряє IP і `warp=on|plus`, фіксує зміни й помилки
в `zen-ips.json`. У schema 2 файлу пауз додано необов'язковий `ips`: останній
підтверджений IP кожного WARP. Лише успішний trace з валідним іншим IP та
`warp=on|plus` скидає квотний і транспортний cooldown цього WARP. За відсутності
binding у старому файлі використовується попереднє успішне IP-спостереження.
Перша перевірка без історії, незмінний IP, помилка й зміна direct не скидають пауз.
Оновлені IP bindings і паузи зберігаються разом до запису історії: старий
`zen-ips.json` не скине свіжу відмову після перезапуску. При збої запису
перехід відкочується в пам'яті для повтору на наступній перевірці.
Номер зміни IP в пам'яті позначає поточне підключення; відкладені квотні чи
транспортні відмови від запитів до зміни IP не повертають старий cooldown.
Інференс та керування реєстраціями монітор не виконує. Перевірки адрес
паралельні, по одному запиту на маршрут; лічильники не скидаються.

`RouteStats` зберігає кумулятивні лічильники Zen у `zen-stats.json` schema 1:
`started_at`, `updated_at`, `routes[direct|host:port].inference` та окремі
`ip_checks`. Модельна спроба записується перед створенням upstream-з'єднання,
429 — після отримання HTTP-статусу, успіх — лише після завершеного SSE без
помилки. Збої з'єднання/потоку враховуються окремо; скасування клієнтом,
локальні cooldown-відмови й Go не збільшують ці помилки. Метрики не зберігають
тіл, ключів чи ID сесій. Власний lock захищає паралельні інкременти й атомарне
збереження; ключ адреси зберігає історію після перестановки чи видалення слотів.
Збій запису залишає дані в пам'яті та виставляє `persistence_error` у `/health`
і `doctor`, не перетворюючи виконану генерацію на помилку. Наступний успішний
запис зберігає всі накопичені зміни. Зламаний історичний файл не обнуляється.

`doctor` представляє ці дані двома таблицями українською. Мапування номерів
WARP на історичні лічильники використовує `zen_proxies[].endpoint`, а не порядок
ключів у файлі статистики. Тому перестановка слотів не переплутує числа.
`doctor --json` повертає повну відповідь `/health` без табличного форматування.
Лише табличний CLI додатково запускає обмежені за часом read-only `docker ps`,
`inspect` і `stats --no-stream` для проєкту `omp-warp`. Порти 8888/tcp зіставляють
статистику контейнерів з адресами маршрутів. Час роботи обчислюється зі
`State.StartedAt` запущеного контейнера, скидається після його перезапуску
та залишається доступним при збої окремого запиту `stats`. Знімок RAM не зберігається як
кумулятивний лічильник; сервер, `/health`, JSON CLI й inference підпроцесів
для цих вимірів не запускають.

Необов'язковий `deploy/warp/compose.yaml` містить десять вузлів WARP +
tinyproxy, по одному контейнеру та volume на реєстрацію. Реєстрація створюється
один раз явною командою; запуск відновлює лише наявне підключення.
tinyproxy може відкривати зовнішні з'єднання тільки через IPv6-інтерфейс WARP;
IPv4 та вихід повз тунель заблоковані для його користувача. Контролера,
перереєстрацій чи БД немає; фонове опитування обмежене читанням IP trace.
Короткий `deploy/start-warp.sh` піднімає ці контейнери, за потреби Colima на
macOS, і робить `exec` звичайного `serve`. HTTP-сервер Python підпроцесів не запускає;
окремий табличний `doctor` лише читає Docker-метрики локально.

Відповідь проходить як послідовність SSE frames, не як буфер усього тексту.
Термінальною подією для Chat Completions вважається `finish_reason`, а не лише
`data: [DONE]`: останнє — конвенція OpenAI, і не кожен шлюз його надсилає.
Схеми справжніх інструментів і їх аргументи не перекодовуються у формат іншого
харнеса. Реальний `edit` виконує OMP; проксі не має коду виконання shell-команд.
Приватні session-поля не доходять до OpenCode.

Для Anthropic Messages підтримано його session/auth-заголовки. OMP нормалізує
base URL з кінцевим `/v1`; локальний маршрут лишається `/zen/v1/messages`.
За відомою політикою OpenCode шлях видаляє непідтримуване `context_management`.
Не передаються довільні beta/header overrides чи cookie клієнта.

## Маршрути

| Локальний маршрут | Upstream |
|---|---|
| `/zen/v1/chat/completions` | `https://opencode.ai/inference/openai/v1/chat/completions` |
| `/zen/v1/responses` | `https://opencode.ai/inference/openai/v1/responses` |
| `/zen/v1/messages` | `https://opencode.ai/inference/anthropic/v1/messages` |
| `/go/v1/<підтримуваний endpoint>` | `https://opencode.ai/zen/go/v1/<той самий endpoint>` |

OMP бачить окремі `opencode-zen-free` та `opencode-go-free`; той самий ID у Zen і Go —
дві окремі моделі, спільного списку немає. Провайдер `opencode-free` і маршрут `/free`
прибрано у 1.3.0: запит на них отримує 404 з назвами двох провайдерів і не
перенаправляється ні в Zen, ні в Go.

Маршрут використовується тільки для відповідного ID у поточному каталозі.
Redirect не виконується. Клієнт не може передати сторонній URL або шлях.
WebSocket, Google native API, realtime, audio/video transport не реалізовані.
Не-чатовий System One (Jev) не підтримується: у OMP немає чим викликати структуроване
оцінювання стану, тож і маршруту для нього немає. Такі ID виключаються як непідтриманий
протокол. Для поточних генеративних free-моделей досліджено Chat Completions/Responses;
Messages підтриманий на рівні протоколу та mock-тестів, не підтверджений live
на всіх потенційних майбутніх free-SKU.

## Каталог і гроші

Якщо офіційна таблиця цін прочитана, тільки вона дає дозвіл: `models.dev` тоді може
підтвердити, але не замінити її. Нульові ціни в `models.dev` використовуються і як
заглушка для ще не тарифікованих моделей, тому самі по собі вони достатні лише коли
таблиця недоступна або не парситься — і це записується в `notes`.

Ціни з документації зіставляються за колонкою Model ID, якщо вона є; інакше за назвою,
і назва, що трапляється в кількох рядках цін, не дає ціни жодному з них.

`GET /models` відповідного OpenCode lane визначає присутність ID.
`models.dev/api.json` дає capability/limit/price metadata; таблиці офіційних
OpenCode docs можуть підтвердити endpoint і Free-ціну. Усі наявні числові costs,
включно з cache/tier, мають бути нульовими. Невідомі/суперечливі дані не
перетворюються на нуль. `-free`, `alpha` або назва підписки не є дозволом.

TTL — 900 секунд. Кеш живе тільки в памʼяті процесу й не використовується після TTL,
якщо нова перевірка неможлива. Ядро моста пише `catalog.json` як звіт, але не
читає його для дозволу на інференс. Розширення може читати його лише для назв
недоступних зараз моделей. Невдала перевірка одного lane не переносить його моделі на інший.
Підтвердження нульових цін за metadata — захисний фільтр, не доказ тарифу
на сервері в конкретну мілісекунду. Сервер може змінити ціну між refresh і POST.
Баланс і підписка Go лишаються під керуванням OpenCode.

`cost: 0` у конфігурації OMP лише відображає локальну оцінку. Цей параметр
**не наказує OpenCode рахувати безкоштовно**. Саме тому існує окремий admission
check до відправлення запиту. Пакет не контролює інші провайдери OMP і не
претендує на глобальний міжпроцесний firewall для всіх витрат користувача.

Нові ID з підтримуваним протоколом і підтвердженим zero-cost додаються через
discovery без нового коду. Невідомий протокол виключається з поясненням.
Це свідома fail-closed межа замість заяви «всі майбутні моделі гарантовано».

## Сесії та reasoning

Хук `before_provider_request` виконується для головного агента, підагентів і Advisor.
Службові виклики OMP (генерація заголовка сесії, commit-повідомлення, класифікатор
складності, вилучення памʼяті) його не викликають — вони йдуть з ідентифікатором
екземпляра розширення в заголовку `x-omp-free-session`.

Канонічний session token генерується у форматі OpenCode: інвертований час у
мілісекундах, малий лічильник та 14 base62-символів. Міст тримає відповідність
між ID сесії OMP і цим token у пам’яті процесу. Це не реєстрація нової
серверної сесії чи засіб отримати нову квоту. Вже правильний token зберігається.
Основний хук використовує session ID OMP. Для helper-запитів без hook є стабільний
ID екземпляра розширення; після перезапуску affinity допоміжних запитів може
змінитися. Пакет не обіцяє точного cache-resume кожного прихованого виклику OMP.

Payload hook фільтрує за провайдером моделі самого запиту (`ctx.model.provider`):
OMP (починаючи з 18.2.0) передає в хук модель конкретного виклику, а не батьківської сесії, тому
Advisor чи підагент на іншому провайдері не зачіпається. Приватний marker у
`compat.extraBody` не використовується: OMP додає `extraBody` лише для
`openai-completions`, тож для Responses-моделей marker ніколи не доходив.

Використовуються точні upstream ID, щоб зберегти розпізнавання сімейства у OMP.
Розширення передає OMP підтримувані API, ліміти та рівні reasoning з перевіреного
каталогу; ключі й endpoints інших провайдерів не копіюються.
Проксі не створює фальшивого reasoning content і не відкидає thinking для
отримання видимого «успіху». Невідомі особливості нового backend лишаються
межами сумісності, які треба перевірити live.

## Інструменти-заглушки

Дописати wire-ім’я — не те саме, що зробити інструмент неможливим для виклику.
Заглушки PR могли лишатися вибором моделі, навіть якщо їх немає в локальному
registry. Zen приймає тільки `tool_choice: auto` або відсутнє значення;
тому міст прибирає несумісний вибір і розпізнає виклики відсутніх інструментів
у стандартних SSE-подіях. Такі виклики завершуються protocol error.
Go зберігає `tool_choice: none` для початково tool-less запиту.

Заглушки не реєструються як локальні OMP tools. Справжні схеми `bash`, `read`,
`edit` тощо не перезаписуються. Активні права OMP не розширюються. Якщо модель
або новий формат потоку несумісні з цією схемою, правильний результат —
помилка, а не непомітне виконання відсутнього інструмента.

## Обмеження ресурсів і обробка відмов

Локального ліміту паралельності немає: валідні запити передаються upstream без черги.
Виняток для повтору поточного запиту — явний `429 FreeUsageLimitError` до SSE;
він переводить незмінний POST на наступний доступний маршрут Zen.
Вибір іншої моделі лишається OMP; квотний cooldown блокує лише відповідний маршрут.
JSON до 32 MiB, SSE frame до 2 MiB. Timeout сокета 120 секунд на операцію;
довгий reasoning без жодних даних може завершитися timeout. При розриві
клієнтського з’єднання закривається upstream. Немає фонового планувальника інференсу; IP-монітор робить лише GET trace.

401/402/403 від OpenCode зупиняють lane на час життя процесу, включно з усіма
виходами пулу. 429 ставить паузу ≥ 60 с. `FreeUsageLimitError` враховує числовий
`Retry-After` повністю й ставить на паузу лише маршрут, який повернув відмову,
з автоматичним переходом на наступний маршрут. Direct-429 не змінює WARP-квоти;
WARP-429 не змінює квоти direct чи інших WARP. Інший Zen-429 також ставить
на паузу лише конкретний маршрут, без повтору поточного POST. HTTP 5xx, помилка
upstream-транспорту (також посеред SSE), не-SSE відповідь та обірваний SSE дають йому 30 с.
Відмова клієнта не штрафує вихід. Нова пауза не скорочує вже відому довшу;
успіх паралельного запиту також її не скидає.
Ні ключі, ні моделі, ні lane не перебираються. Порожній/обірваний потік не
позначається як успішний завершений результат.

**Розпочата генерація та SSE не повторюються.** Лише явна квотна відмова до SSE
дозволяє наступний POST на ще не використаному маршруті. Якщо всі виходи на
паузі, `503 ZenProxyCooldown` містить найближчий дедлайн; повідомлення про
вичерпання всіх виходів не створюється через одну відмову. OMP має власні
повторні спроби/ролі/fallback, які цей пакет не переписує. Перезапуск моста
не скидає збережені квотні паузи.

## Безпека й залишкові ризики

Loopback не є захистом від іншого процесу того самого користувача. Тому є
локальний випадковий bearer, перевірка Host і відмова browser-Origin.
Ключ Go зберігається лише в проксі та його локальному secret-файлі;
body/key не пишуться в access log. Типові HTTP error messages очищуються від
відомого upstream key. Довільний model output не є повним DLP/redaction сервісом.

Перевірка TLS не вимикається. Upstream хост і шляхи фіксовані, redirects не
переслідуються. Немає читання auth-файлів OpenCode/OMP або browser cookies.
Файли стану довірені на рівні вашого локального користувача; це не sandbox
проти зловмисника, який уже може переписувати вашу конфігурацію або код.

Весь текст/код/зображення, що ви відправили, отримує сервіс моделей. Приватність
free-tier визначає OpenCode та upstream, не локальний проксі. Account restrictions,
квота, регіональна доступність і зміни невідомого gate залишаються поза контролем
пакета. 13 жовтня 2026 OMP → Zen підтверджено текстовою відповіддю, `bash` і
запитом без інструментів. 17 жовтня 2026 на OMP 18.11.3 повторно підтверджено
повний цикл `read` через Zen. Go повернув 403 через завершення підписки, як і
нативний провайдер OMP; успішну відповідь Go після цієї зміни не підтверджено.
19 жовтня на macOS підтверджено реальний перехід 429 → 200 між WARP-виходами
в одному звичайному процесі та одній сесії. Точний протокол — у
[дослідженні](ДОСЛІДЖЕННЯ.md#16-пул-у-звичайному-запуску-й-автоматичне-перемикання-після-429).

## Перевірки

140 Python-тестів покривають admission, direct → десять WARP, окремі cooldown,
підтвердження зміни IP, захист від запізнілих відмов, збереження статистики,
таблиці doctor, RAM і час роботи, скасування й цілісність SSE. CONNECT/TLS перевіряється
справжніми локальними сокетами; тестовий самопідписаний сертифікат і відкритий
тестовий ключ лежать у `tests/fixtures/connect-test.pem` і використовуються
лише для цих loopback-тестів. 15 JavaScript-тестів перевіряють контракт OMP.
Ці тести працюють без зовнішньої мережі, ключів OpenCode та генерацій моделі.
