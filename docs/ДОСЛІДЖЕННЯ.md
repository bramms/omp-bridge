## Висновок

Ці PR підтверджують конкретну проблему сумісності та показують технічний спосіб
сформувати прийнятні запити. **Вони не доводять, що всі free-моделі вже стабільно
працюють у штатному випуску OMP, в усіх допоміжних режимах і на будь-якому акаунті.**

Нульовий баланс Zen та вимкнений Use balance не є причиною `FreeTierError` самі
по собі. Слід відокремлювати перевірку клієнта, авторизацію, квоту, доступність
моделі та її платний/безкоштовний SKU.

## 2. Чотири перевірки в дослідженні спільноти

У [коментарі до issue #12306 від 18 вересня](https://github.com/can1357/oh-my-pi/issues/12306#issuecomment-5726093352)
описано послідовне вилучення одного параметра із запиту. Заявлені умови:

1. Перший токен User-Agent має форму `opencode/<version>`.
2. `x-opencode-session` має форму `ses_` + 12 малих hex-символів + 14 alnum.
3. Генеративний запит містить `stream: true`.
4. У tools присутні конкретні назви `bash`, `edit`, `glob`, `grep`, `read`.

Не будь-які п’ять назв, не просто `bash` і не лише додатковий HTTP-заголовок.
Цим пояснюється, чому простий проксі заголовків може пропускати основний turn,
але не Advisor/summary. Повідомлення про обов’язковий мінімальний номер версії
клієнта в ранньому PR не було відтворене пізнішим бісектом; не вважаємо його
встановленим фактом. Значення `1.18.31` було дослідженим у PR варіантом,
а не вимога встановлювати OpenCode CLI цієї версії.

13 жовтня [pi-freeflow PR #45](https://github.com/trefeon/pi-freeflow/pull/45)
зафіксував актуальний набір із **шести** назв, додавши `write`. Це PR лише
до документації: робоча реалізація вже була в pi-freeflow. У цьому мості
ізольований тест показав, що навіть шість інструментів, streaming і потрібні
заголовки не рятують ID із випадковими молодшими 12 бітами часу. Генерація
лічильника OpenCode починаючи з 1 дала HTTP 200 для `cat-jam-free` в OMP.
Версія User-Agent у цьому тесті — `opencode/1.19.0`.

Це результати авторів і коментаторів, не опублікований контракт gateway.
Правило може змінитися без сумісного оновлення API.

## 3. Офіційний Go і free tier — не тотожні речі

[Документація Go](https://opencode.ai/docs/go/#where-can-i-use-it) дозволяє
сторонні coding agents із належним характером трафіку, власним User-Agent і
стабільним session ID. Це не автоматичне схвалення видавання іншого клієнта за
OpenCode для обмеженого безкоштовного пулу.

Модель, включена у Go-підписку, може мати ненульову облікову ціну та витрачати
ліміт підписки. У цьому пакеті **free** означає підтверджений нульовий тариф,
а не «вже сплачений у місячній підписці». Наприклад, Muse Contributor без
`-free` та Muse Contributor Free — різні ID. Вони не взаємозамінні.

Use balance — окремий механізм витрачання Zen credits після Go-ліміту.
Пакет не вмикає його, не викликає платний SKU і не переводить невдалий free-запит
на інший тариф. Джерело: [Usage beyond limits](https://opencode.ai/docs/go/#usage-beyond-limits).

## 5. Ризик акаунта та конфіденційність

У [коментарі від 17 вересня](https://github.com/can1357/oh-my-pi/issues/12306#issuecomment-5713586792)
тестувальник повідомив про `[user_blocked]` і повідомлення сервісу щодо
повторних порушень політики після серії досліджень. Не встановлено, що саме
стало причиною; це не доказ неминучого блокування кожного стороннього клієнта.
Проте ігнорувати таке повідомлення було б неправильно.

Саме тому compat-режим потребує явного прапорця, а 401/402/403 зупиняють
канал у проксі. Немає підбору ключів, ротації акаунтів, обходу регіонів,
відновлення заблокованого доступу або нескінченних повторних проб.

Free/contributor-моделі не слід прирівнювати до приватного локального інференсу.
Офіційний розділ [Zen Privacy](https://opencode.ai/docs/zen/#privacy) описує
використання даних для окремих free/contributor пропозицій, зокрема навчання,
та обмеження щодо конфіденційних/персональних даних для trial-моделей.
Проксі не анонімізує ваш код і не змінює ці умови. Не надсилайте секрети,
API-ключі, персональні дані або закритий код без належного дозволу.

## 6. Чому не CLIProxyAPI, OpenCode server або форк OMP

Звичайна переадресація HTTP не виправляє body-gate. Запуск `opencode run`,
`opencode serve`, SDK/ACP поверх запущеного OpenCode або іншого CLI-агента
не відповідає меті проєкту. Масивний PR-форк OMP додавав би витрати
на збірку та конфлікти оновлень.

Тут агентом залишається штатний OMP. Локальна обгортка змінює лише мережевий
запит, перевіряє дозволений тариф і повертає стандартний потік у той самий
OMP. Розширення використовує офіційні `registerProvider`, per-model `api`,
`before_provider_request` та `registerCommand`.

Документація OMP: [models](https://github.com/can1357/oh-my-pi/blob/main/docs/models.md),
[extensions](https://github.com/can1357/oh-my-pi/blob/main/docs/extensions.md),
[extension-loading](https://github.com/can1357/oh-my-pi/blob/main/docs/extension-loading.md).

## 7. Reddit і рівень незалежного підтвердження

Пошук включав комбінації `OpenCode free tier OMP`, `oh-my-pi FreeTierError`,
`12326`, `12556`, `OpenCode Go alternatives` із обмеженням на Reddit.
Не знайдено придатного незалежного допису, який підтверджує **всі** умови:
нативний OMP, без OpenCode CLI, безкоштовні SKU, баланс 0, Use balance OFF,
успішний завершений інференс та інструменти.

Це результат проведеного пошуку, а не твердження, що такого допису ніде немає.
Загальні обговорення Go або відгуки про платні моделі не використані як доказ
працездатності цього пакета. Основні технічні джерела — офіційні docs, код
проєктів, PR та відтворювані описи бісекту в GitHub.

## 8. Що ще треба перевірити на реальному акаунті

Потрібні завершена live-відповідь кожного ID, нативний read/edit tool loop,
reasoning replay на наступному turn, хоча б один Advisor/обмежений worker,
регіональна доступність Muse, фактичні квоти та незмінність балансу.
У пакеті є діагностика (`bridge.py probe`), але її результати не вигадані та
не позначені як виконані. Статус першого релізу: **реалізовано; локальні тести пройдені;
production/live-сумісність на той момент не підтверджена**. Актуальне
оновлення наведено нижче.

## 9. Зміна шлюзу 14 жовтня 2026 року

Після переходу OpenCode на V2 старий `POST /zen/v1/chat/completions`
повертав `403 FreeTierError` для OMP та свіжого pi-freeflow v1.36.1. Такий
самий запит через офіційний OpenCode V2 з `space-bunny-free` працював.
[Нова документація Inference API](https://dev.opencode.ai/v2/docs/console/api/inference)
вказує на `/inference/openai/v1/chat/completions`; стара Zen-адреса більше
не є робочою точкою для цього сценарію.

Ізольоване порівняння реальних HTTP-запитів виявило потрібні для free-запиту
`Authorization: Bearer public`, `x-opencode-session`,
`x-opencode-session-id`, валідні схеми інструментів і відсутність одночасної
пари `x-session-affinity` + `x-opencode-request`. Набір інструментів, який
штатний OMP надсилає під час роботи, пройшов цю перевірку без підміни
самих інструментів. Для діагностики без OMP заглушки повинні мати хоча б
одне поле в JSON-схемі. Каталог тепер бере ціну і формат з
[документації моделей V2](https://dev.opencode.ai/v2/docs/console/models),
а не зі старої Zen-сторінки, що відповідає перенаправленням.

Після зміни production-проксі `space-bunny-free` повернув підтверджену
відповідь HTTP 200. Нативний OMP через активний міст прочитав випадковий
локальний файл інструментом і повернув його точний вміст. Це перевіряє
поточну роботу тексту й одного циклу інструмента; решта моделей та
довготривала стабільність не перевірені. Сумісність із free tier залишається
неофіційною: шлюз може знову змінити правила, і 403 має зупиняти Zen
без платного запасного маршруту.

Повідомлення про той самий збій:
[OMP #12306](https://github.com/can1357/oh-my-pi/issues/12306),
[OmniRoute #13935](https://github.com/diegosouzapw/OmniRoute/issues/13935),
[OpenCode #55435](https://github.com/anomalyco/opencode/issues/55435).
[pi-freeflow PR #45](https://github.com/trefeon/pi-freeflow/pull/45)
описує старі вимоги сумісності, але не виправляє зміну V2.

## 10. Стан на 17 жовтня 2026 року

OMP 18.11.3 знаходить розширення і через `~/.omp/agent/extensions/`, і через
явний `-e`. Каталог на цю дату пропустив дев'ять Zen-моделей
(`beam-free`, `big-pickle`, `deepseek-v4.1-flash-free`, `glm-5.3-flash-free`,
`longcat-2.5-preview-free`, `mimo-v2.6-flash-free`,
`nemotron-3.5-lightning-free`, `nemotron-3.5-super-vl-free`,
`space-bunny-free`) і дві Go (`beam-free`, `longcat-2.5-preview-free`).
Таблиця в розділі 4 — історичний знімок 20 вересня; актуальний список завжди
дає `python3 bridge.py catalog`.

Наживо перевірено: `omp -p --no-extensions -e extension.mjs` з моделлю
`opencode-zen-free/big-pickle` прочитав випадковий файл інструментом `read`
і повернув його точний вміст. Тобто міст працює з чистим OMP без будь-яких
інших розширень, профілів чи обгорток.

У 1.4.0 прибрано локальний ліміт у два одночасні upstream-запити: OMP із
підагентами легко впирався в нього і отримував локальну 409, хоча сам шлюз
запит би прийняв. Квоти й 429 і далі обробляє сервіс, а cooldown після 429
лишився.

## 11. HTTP CONNECT і перевірка WARP 18 жовтня 2026 року

Додано `serve --zen-proxy http://HOST:PORT`: один явно вибраний HTTP CONNECT
для генерації Zen, без пулу та повторів. Go і discovery залишаються прямими.
Політика ціни, стабільні сесії та наявні паузи після відмов не змінені.

Перевірка виконана у двох тимчасових Linux/arm64-контейнерах у Colima на
macOS. Використано офіційний Cloudflare WARP `2026.8.2110.0` у native proxy
mode (`127.0.0.1:40000`), без tinyproxy. Маршрут самої macOS не змінювався.

| Перевірка | Спостереження |
|---|---|
| Адреса через `/cdn-cgi/trace` самого `opencode.ai` | Обидва WARP-клієнти: `104.28.201.202`, `warp=on`; прямий вихід має іншу адресу, `warp=off` |
| Одна ручна перереєстрація WARP B | Знову `104.28.201.202`; незалежного другого WARP-IP не отримано |
| Контрольний запит напряму | `429 FreeUsageLimitError` |
| Той самий запит через WARP A | `429 FreeUsageLimitError` |
| Запит до моделі через WARP B | Не надсилався: IP збігається з A, для якого вже отримано відмову квоти |
| Зовнішній HTTPS-потік через WARP A | `httpbin.org/drip`: HTTP 200, усі 20 байтів за 20,78 с |
| Відключення WARP A | CONNECT-з'єднання відхилене (`ConnectionRefusedError`), прямого fallback немає |

Два звернення до моделі використовували `big-pickle`, однакові тіло та
канонічну сесію, підтверджений свіжим каталогом нульовий тариф, без особистого
API-ключа. SHA-256 підготовленого тіла збігся. Відповіді вказали скидання
квоти на 19 жовтня, 00:00 UTC (03:00 за Києвом). Квоту навмисно не
виснажували, відхилені запити на тому самому виході не повторювали.

**Висновок:** HTTP CONNECT і мережевий вихід через WARP працюють у цьому
середовищі. Користь різних IP для доступної модельної квоти не підтверджена;
два незалежні WARP-виходи отримати в цій обмеженій перевірці не вдалося.
Це не доводить глобального обліку квоти або відсутності користі за інших
адрес/умов. Пулу та автоматичних перереєстрацій не додано.

Додаткова перевірка коду стороннього проєкту: `rotate_warp()` робить до
чотирьох перереєстрацій і явно повторює спробу, якщо адреса лишилася тією
самою. `dedupe` вимикає зайві вузли, якщо різних адрес отримати не вдалося.
Отже, збіг IP очікується самою реалізацією, а одна наша спроба не визначає
кількості доступних адрес. Важлива межа порівняння: сторонній проєкт
використовує full-tunnel WARP + tinyproxy і перевіряє IP через ipify/ifconfig;
наш мінімальний дослід використовував native proxy і trace на OpenCode.
Повного відтворення їхнього алгоритму добору різних IP не виконували.

81 тест Python пройшов на 3.10, 3.13 та 3.14; 15 тестів розширення також
пройшли. Нові локальні перевірки покривають CONNECT, SNI та перевірку довіри
до TLS-сертифіката цілі, поступове SSE, відмову проксі без повторів/fallback
і збереження прямого Go-маршруту. Зовнішній HTTPS-потік не є доказом довгого
модельного SSE: генерація в live-перевірці не почалася через 429.
Тестові WARP-реєстрації та контейнери видалені, Colima повернуто у вимкнений
стан. Постійної мережевої інфраструктури не встановлено.

### Висновок і межі

**Різні вихідні IPv6 на OpenCode отримано. Усі 4 з 4 перереєстрацій B
змінили його IPv6; IPv4 на ipify в усіх вимірюваннях лишився спільним.**

У фінальному контролі A і B мали різні IPv6 та різні префікси /64.
Усі команди реєстрації завершилися успішно; відмов 429 від WARP CLI не було.

Це уточнює результат попереднього native-proxy тесту: там OpenCode бачив
IPv4, у відтвореному full-tunnel + tinyproxy — IPv6. Перевірка одного лише
IPv4 на ipify пропускає цю різницю. Метод добору IPv6 або точну причину
незмінності IPv4 на серверах Cloudflare цей експеримент не розкриває.

Для нашого середовища не слід переносити `dedupe` без змін: його основний
вимір через api.ipify.org успішно повертав би однакові IPv4 і не врахував би
різні IPv6 на OpenCode. Це висновок зі зіставлення коду й отриманих адрес,
а не результат запуску самого dedupe (він у тесті не запускався).

Різні адреси **не доводять незалежних модельних квот**. У цьому досліді не
було жодного запиту до моделей, виклику engine, ротації ключів OpenCode
або додавання пулу в omp-bridge. Порівняння доступної генерації/квоти лишається
окремим можливим дослідом.

### Інші механізми стороннього проєкту

Перевірений мережевий шлях відповідає їхньому WARP + tinyproxy. Для
керування в досліді виконували ту саму послідовність WARP CLI-команд;
автоматичні служби замінено обмеженим тестовим сценарієм.

Окрім цього, сторонній engine має прив'язку сесії до початкового проксі,
перемикання між готовими маршрутами та cooldown після помилок. Це способи
використання вже наявних виходів, а не отримання нових WARP-IP.

Підтримка власних proxy URL / `proxyfile` дозволяє використати інші доступні
виходи. Окремий маркер `pool+` або `#pool` призначений для зовнішнього
провайдера, який сам змінює вихід на новому з'єднанні. Він не змушує WARP
чи tinyproxy видавати іншу адресу. Для поточного досліду ці можливості
не використовувалися.

Джерела: [вибір і стан маршрутів](https://github.com/jasonxu114514/opencode2api/blob/a9470df4fca93a47d7ec58febcbc63100af88644/internal/gateway/pool.go),
[proxyfile і маркер зовнішнього пулу](https://github.com/jasonxu114514/opencode2api/blob/a9470df4fca93a47d7ec58febcbc63100af88644/internal/config/proxy.go).

## 14. Прямий вихід проти WARP IPv6 19 жовтня 2026 року

**Стан: рівно два модельні POST завершено; практичну користь WARP IPv6 підтверджено в цьому порівнянні.**

За запитом користувача порівнюються рівно два одиночні запити: напряму та
через WARP + tinyproxy/IPv6. Модель — `big-pickle`, нульову ціну повторно

`Bearer public`.

Прямий клієнт і WARP-клієнт працюють на тому самому Ubuntu/Python/OpenSSL
image у Colima, в окремих мережевих просторах. У прямому клієнті WARP
daemon не запускається і HTTP-проксі не використовується. Для другого
маршруту — повний WARP-тунель та tinyproxy у спільному мережевому просторі.

Безпосередньо перед кожним POST виконується trace на `opencode.ai`;
модельний запит надсилається на тому самому TLS-з'єднанні. Для прямого
виходу очікується `warp=off`, для WARP — `warp=on` та IPv6. Повторне
підключення після trace заборонене. Ліміт — один модельний POST на маршрут,
без автоматичних повторів, пулу й навмисного вичерпування квоти.

Критерій практичної користі цього порівняння: прямий запит отримує
`429 FreeUsageLimitError`, а однаковий запит через WARP — завершену

лічильника або пропорцію приросту квоти.

## 15. Мінімальний пул трьох WARP-вузлів, 19 жовтня 2026 року

**Стан: пул реалізовано й перевірено. Три постійні реєстрації дають різні IPv6,
але перепідключення змінює публічні адреси без перереєстрації.**

На явний запит користувача додано повторюваний `--zen-proxy` (1–3 різні
адреси), прив'язку сесії, cooldown окремого виходу й вибір наступного
доступного на наступне звернення. Один вхідний запит усе ще означає не більше
одного модельного POST. Після початку SSE перемикання немає.

Реалізація власна, лише стандартна бібліотека. Код GPL-рушія opencode2api
не копіювався. Немає rotator, dedupe, БД, фонового health-check чи автоматичної
перереєстрації. `deploy/warp` містить три контейнери, кожен із WARP + tinyproxy
та окремим volume реєстрації. Початкова реєстрація кожного вузла виконується
явно один раз; старт лише під'єднує вже зареєстрований клієнт.

Параметри cooldown: 429 ≥ 60 с, для `FreeUsageLimitError` повний числовий
`Retry-After`; 5xx, помилка upstream-з'єднання, не-SSE відповідь та обірваний
SSE — 30 с. У пулі 429 консервативно закриває конкретний вихід для всіх моделей.
401/402/403 зупиняють увесь lane. Якщо доступних виходів немає — локальний
`503 ZenProxyCooldown`, без мережі. Коротша нова пауза та паралельний успіх
не скидають довшу. Прив'язки (до 10 000) і паузи — лише в пам'яті процесу.

Мережеві правила tinyproxy дозволяють нові зовнішні з'єднання лише через
WARP IPv6. Прямий вихід та IPv4 для них заблоковано; DNS на loopback та
відповіді локальному клієнтові дозволені. Це запобігає тихому поверненню
до спільного IPv4. Реєстрації сталі, але WARP не гарантує незмінних публічних IP.

Збірку та первинні команди звірено з [офіційним репозиторієм пакетів](https://pkg.cloudflareclient.com/)
і [Linux-інструкцією WARP](https://developers.cloudflare.com/warp-client/get-started/linux/).
У цьому тесті зафіксовано пакет `2026.8.2110.0`, три первинні реєстрації
рознесено на 90 с. Автоматичні повторні реєстрації не виконуються.

## 16. Пул у звичайному запуску й автоматичне перемикання після 429

**19 жовтня 2026 року. Стан: пул увімкнено у звичайному фоновому запуску;
реальний сценарій 429 → наступний запит тієї самої сесії → 200 підтверджено.**

На запит користувача звичайний `serve` тепер читає
`~/.config/omp-free-bridge/zen-proxies.json` (або `$OMP_FREE_HOME/zen-proxies.json`).
Три повторені CLI-прапорці більше не потрібні. Явні `--zen-proxy` перевизначають
файл; відсутній файл або `[]` зберігає прямий режим. Помилковий чи недоступний
файл зупиняє запуск, без тихого прямого fallback.

На цьому Mac налаштування збережене з трьома адресами `127.0.0.1:18090–18092`.
Наявний LaunchAgent `local.omp-bridge` переведено на `deploy/start-warp.sh`:
він за потреби піднімає Colima, запускає ті самі три контейнери та передає
керування звичайному `bridge.py serve --compat-opencode`. Нового LaunchAgent
чи сервісу керування немає; ядро моста залишається без subprocess і залежностей.
Початковий plist збережено приватно як `local.omp-bridge.plist.before-warp`.
Compose CLI встановлено як плагін поточного користувача; SHA-256 бінарника
перевірено за digest офіційного релізу v5.6.0.

Реєстрації з попереднього тесту використано повторно, `registration new/delete`
не виконується. Автозміна тут означає вибір іншого наявного виходу після 429,
а не створення нової WARP-реєстрації. Один вхідний запит — не більше одного
модельного POST; перемикання застосовується до наступного звернення сесії.
Відповіді Zen отримують діагностичний `X-OMP-Zen-Proxy: 1|2|3`, включно з 429.
Це дає перевірити вибір у звичайному працюючому процесі без підміни connector.

## 19. Виправлення області квотного cooldown, 23 жовтня 2026 року

маршрутизатором за старим дедлайном. Перевірка спростувала припущення, що
збережена до зміни IP відмова описує поточну доступність кожного маршруту.

У межах цього запиту виконано лише діагностику: код, кулдауни й процес
моста не змінювались, загалом зроблено шість модельних POST без повторів.
Ці зовнішні звернення, як попередні ручні trace, не входять до лічильників
HTTP-сервера. Повні відповіді з HTTP-заголовками та IP збережено приватно:
`~/.config/omp-free-bridge/deepseek-post-restart-check-2026-10-23.json`.


## 27. Скидання паузи тільки WARP із новим IP, 23 жовтня 2026 року

У 1.8.2 успішний GET trace від OpenCode із валідним іншим IP та
`warp=on|plus` скидає квотний і транспортний cooldown лише відповідного WARP.
Порядок direct → 1–8 зберігається. Перша перевірка без попереднього IP,
незмінний IP, помилка GET, невалідна адреса та `warp=off` пауз не скидають.
Зміна direct також не скидає його чи чужі дедлайни. Лічильники накопичувальні.

До schema 2 `zen-cooldowns.json` додано необов'язковий `ips` — останні
підтверджені адреси WARP разом із квотними/транспортними дедлайнами. Старі
файли без `ips` використовують попередній успішний запис `zen-ips.json` як
початкову історію. Новий binding з паузами записується атомарно до історії IP;
застарілий файл історії не скине свіжу відмову при наступному запуску. Збій
запису відкочує перехід у пам'яті для повторної перевірки. Запити позначені
номером зміни IP: відкладена квотна чи транспортна відмова запиту до зміни
адреси не поверне стару паузу після її скидання.

132 Python-тести та 15 JavaScript-тестів пройшли. Нові регресії перевіряють
ізоляцію зміненого WARP серед восьми, збереження direct та решти семи,
помилкові/незмінні trace, перезапуск і перестановку слотів, застарілу історію
при новій відмові, збій запису, невалідний binding, запізнілу 429 та повернення
до звичайного автоматичного fallback зі збереженням тіла запиту.

Живий тест виконувався в окремому тимчасовому екземплярі нового моста з
тими самими вісьмома WARP та справжнім allowlist. Лише в його копії стану
відкрито WARP 1 для повторної перевірки й WARP 3–4 як уже перевірені доступні.
Один модельний запит отримав реальну `429 FreeUsageLimitError` через WARP 1
(`Retry-After: 36405`), пропустив відому паузу WARP 2 й автоматично завершився
через WARP 3: HTTP 200, точний `BRIDGE_OK`, завершений SSE, без tools.
Робочий файл квот і робочі лічильники цей тест не змінював. Приватний протокол:
`~/.config/omp-free-bridge/ip-cooldown-fix-live-failover-2026-10-23.json`.

Після перевірки відсутності активних локальних inference-з'єднань зупинено
робочий міст, збережено приватний знімок стану й видалено лише квотні паузи
WARP 3–4, їхні транспортні таймери встановлено в нуль. Поточні IP цих двох
повторно підтверджені trace та збіглися з адресами успішних модельних перевірок.
Після запуску 1.8.2 PID змінився 35608 → 60795. Усі вісім контейнерів зберегли
ID і час запуску; повторних WARP-перезапусків не було. Квоти direct, 1, 2, 5,
6, 7, початок обліку й усі попередні модельні лічильники збережено.

Звичайний запит до оновленого робочого моста автоматично вибрав WARP 3:
HTTP 200, `X-OMP-Zen-Proxy: 3`, точний `BRIDGE_OK`, завершений SSE без tools
за 2,757 с. Лічильники тільки WARP 3 збільшились на одну спробу й один успіх;
429 і транспортні помилки не додались. WARP 3–4 залишилися без локальної паузи,
блокувань каналу та помилок IP-монітора немає. Протоколи розгортання й перевірки:
`ip-cooldown-fix-deploy-2026-10-23.json` та
`ip-cooldown-fix-production-probe-2026-10-23.json` у приватному каталозі стану.

Під час фінального `doctor` один цикл IP-монітора WARP 4 записав `ValueError`.
Наступний автоматичний цикл успішно підтвердив той самий IP і очистив поточну
помилку; додатковий ручний trace повернув HTTP 200, `warp=on`, а `warp-cli`
