# Посібник користувача

Усе, що треба, щоб запустити міст, підключити його до OMP, вибрати модель і
зрозуміти, що означає кожна помилка. Як влаштовано всередині — в
[архітектурі](АРХІТЕКТУРА.md), чому саме так — у [дослідженні](ДОСЛІДЖЕННЯ.md).

[Статистика doctor](#doctor) · [Перезапуск WARP](#перезапуск-warp) ·
[Усі команди](#7-команди)

## 1. Що потрібно

| Що | Навіщо |
|---|---|
| [Oh My Pi](https://github.com/can1357/oh-my-pi) (`omp`) | Агент, який і далі робить усю роботу. Перевірено на 18.11.3. |
| Python 3.10+ | Сам міст. Лише стандартна бібліотека, `pip install` не потрібен. |
| Доступ до `opencode.ai` і `models.dev` по HTTPS | Каталог моделей і сам інференс. |
| API-ключ OpenCode Go і активна підписка | **Тільки** для провайдера `opencode-go-free`. Zen працює без ключа. |
| Node.js 18+ | Тільки щоб запускати JavaScript-тести. Для роботи не потрібен. |
| Docker із Compose, Bash; на macOS також Colima | Тільки для необов'язкового пулу WARP. |

Для прямого режиму OpenCode CLI, Docker, npm-пакети й патчі OMP не потрібні.
Міст перевірено на Linux та macOS. На macOS також перевірено пул WARP, прямий маршрут і контроль фактичних IP; інструкції автозапуску нижче є для обох ОС.

## 2. Встановлення

Тека може бути будь-яка, далі в прикладах — `~/.local/share/omp-free-bridge`:

```sh
git clone https://github.com/bramms/omp-bridge.git ~/.local/share/omp-free-bridge
cd ~/.local/share/omp-free-bridge
python3 bridge.py catalog | head -40
```

`catalog` нічого не надсилає моделям: він тільки збирає список, перевіряє
ціни й показує, що пропущено (`models`) і що відкинуто з причиною
(`excluded`). Якщо `models` порожній — міст не запуститься, і це правильно.

## 3. Запуск моста

```sh
python3 bridge.py serve --compat-opencode
```

Міст слухає тільки `127.0.0.1:8765` і пише в консоль, скільки маршрутів
пройшли перевірку. Зупинка — `Ctrl+C`.

**Без `--compat-opencode` Zen відповідає `403 FreeTierError`.** Прапорець
вмикає неофіційну сумісність: запит має форму, яку шлюз очікує від OpenCode
(див. [дослідження](ДОСЛІДЖЕННЯ.md), розділи 2 і 9). Він навмисно не
вмикається сам — ви приймаєте цей ризик явно.

Параметри `serve`:

| Параметр | За замовчуванням | Що робить |
|---|---|---|
| `--port N` | `8765` | Локальний порт. Розширення дізнається його з `runtime.json` саме. |
| `--compat-opencode` | вимкнено | OpenCode-подібні заголовки й заглушки інструментів. |
| `--opencode-version X.Y.Z` | `1.19.0` | Версія в `User-Agent: opencode/…` у compat-режимі. |
| `--zen-proxy http://HOST:PORT` | `zen-proxies.json`; без файла — напряму | Явно перевизначити збережений пул; повторити 1–8 разів; це запасні виходи після прямого маршруту. |

Наприклад, якщо у вас уже працює локальний HTTP-проксі:

```sh
python3 bridge.py serve --compat-opencode --zen-proxy http://127.0.0.1:18090
```

Звичайний `serve` сам читає `zen-proxies.json` із теки стану (за замовчуванням
`~/.config/omp-free-bridge`). Це JSON-масив адрес HTTP-проксі. `[]` вимикає пул.
Помилковий чи недоступний файл зупиняє запуск, без тихого прямого fallback.

TLS до `opencode.ai` перевіряється всередині CONNECT-тунелю. Go та завантаження
каталогу залишаються прямими. Підтримується лише `http://HOST:PORT`, без логіна,
пароля чи шляху; SOCKS5 та `https://`-проксі не підтримуються. Адреси мають бути
різними. Zen спочатку пробує прямий маршрут, а після відмови квоти автоматично
проходить WARP 1 → … → 8, пропускаючи маршрути на паузі.

### Вісім вузлів WARP (необов'язково)

Потрібні Docker із Compose та Linux із `/dev/net/tun`; на macOS — наприклад,
Colima. Сам міст і прямий режим Docker не потребують. Конфігурація містить
вісім вузлів: WARP і tinyproxy разом у кожному, порти лише на loopback.
Користувач, від якого запускається міст, повинен мати доступ до Docker engine.

На macOS спочатку підніміть Colima й виберіть її контекст для поточного термінала:

```sh
colima start --activate=false --save-config=false
export DOCKER_CONTEXT=colima
```

На Linux цей крок пропустіть. Зберіть image і запустіть вісім вузлів:

```sh
docker build -t omp-bridge-warp:local deploy/warp
docker compose -f deploy/warp/compose.yaml up -d --no-build
```

Один раз для **кожного** вузла `warp-a`–`warp-h` виконайте, підставивши
ім'я замість `warp-a`. Між початковими реєстраціями зачекайте 90 с:

```sh
docker compose -f deploy/warp/compose.yaml exec warp-a warp-cli --accept-tos registration new
docker compose -f deploy/warp/compose.yaml exec warp-a warp-cli --accept-tos mode warp
docker compose -f deploy/warp/compose.yaml exec warp-a warp-cli --accept-tos connect
docker compose -f deploy/warp/compose.yaml exec warp-a warp-cli --accept-tos status
```

Це явне початкове налаштування за [інструкцією Cloudflare](https://developers.cloudflare.com/warp-client/get-started/linux/).
Реєстрації лежать у восьми окремих volumes. Перезапуск використовує їх повторно;
автоматичних `registration new/delete` немає. Не запускайте початкову реєстрацію
повторно й не видаляйте volumes (`down -v`), якщо хочете зберегти ці вузли.

Дочекайтеся `Status update: Connected` на кожному вузлі. Перед використанням
перевірте `warp=on` і **вісім зовнішніх адрес** саме на OpenCode:

```sh
curl --max-time 20 --proxy http://127.0.0.1:18090 https://opencode.ai/cdn-cgi/trace
curl --max-time 20 --proxy http://127.0.0.1:18091 https://opencode.ai/cdn-cgi/trace
curl --max-time 20 --proxy http://127.0.0.1:18092 https://opencode.ai/cdn-cgi/trace
curl --max-time 20 --proxy http://127.0.0.1:18093 https://opencode.ai/cdn-cgi/trace
curl --max-time 20 --proxy http://127.0.0.1:18094 https://opencode.ai/cdn-cgi/trace
curl --max-time 20 --proxy http://127.0.0.1:18095 https://opencode.ai/cdn-cgi/trace
curl --max-time 20 --proxy http://127.0.0.1:18096 https://opencode.ai/cdn-cgi/trace
curl --max-time 20 --proxy http://127.0.0.1:18097 https://opencode.ai/cdn-cgi/trace
```

Збережіть пул один раз, і він підключатиметься при звичайному запуску:

```sh
bridge_state="${OMP_FREE_HOME:-$HOME/.config/omp-free-bridge}"
mkdir -p "$bridge_state"
install -m 600 deploy/zen-proxies.json "$bridge_state/zen-proxies.json"
bash deploy/start-warp.sh --compat-opencode
```

`start-warp.sh` запускає наявні вісім контейнерів, потім замінює себе процесом
моста. На macOS він спочатку піднімає Colima, якщо та вимкнена; на Linux
використовує поточний Docker engine. Потрібні встановлені Docker Compose та,
на macOS, Colima. Image має бути зібраний, реєстрації — створені кроками вище;
лаунчер їх не створює і не перевипускає. Інтерпретатор можна задати через
`OMP_FREE_PYTHON` (за замовчуванням `python3`). Якщо WARP уже працює, достатньо
звичайного `python3 bridge.py serve --compat-opencode` — він читає той самий файл.

Для Colima додавайте `--context colima` до команд Docker. WARP-реєстрації сталі,
але Cloudflare може змінити публічну адресу; це не послуга виділених статичних IP.
Міст сам не створює реєстрацій. Щохвилини він перевіряє фактичні адреси через
`opencode.ai/cdn-cgi/trace` та показує дублікати в `doctor`.
Якщо успішний trace підтвердив інший валідний IP і `warp=on|plus`, міст скидає
стару квотну та транспортну паузу лише цього WARP. Він знову бере участь у
звичайній черзі direct → 1–8. Перша перевірка без попереднього відомого IP,
незмінний IP, помилка trace або `warp=off` нічого не скидають. Direct та інші
вузли не зачіпаються. Новий IP не гарантує квоти: нова 429 знову поставить
цей маршрут на паузу. ID реєстрації та накопичені лічильники зберігаються.
tinyproxy відкриває зовнішні з'єднання лише через WARP IPv6: коли тунель
від'єднано, прямого чи IPv4 fallback немає.

Порядок для всіх сесій однаковий: direct → WARP 1 → … → WARP 8.
Квотний або транспортний cooldown виключає лише відповідний маршрут до його
reset або підтвердженої зміни IP цього WARP. Щойно direct відновлюється,
він знову має пріоритет.

`429 FreeUsageLimitError` до початку SSE ставить лише вибраний маршрут на паузу
за повним числовим `Retry-After` (мінімум 60 с) і автоматично повторює незмінний
запит через наступний доступний маршрут. Тіло, модель та ID сесії зберігаються;
кожен маршрут використовується не більше одного разу в межах запиту. Квота
інших маршрутів не змінюється. Коли всі виходи на паузі, повертається
`503 ZenProxyCooldown` із найближчим reset.

Мережевий збій дає маршруту паузу 30 с; лише наступне звернення може вибрати
інший вихід. Поточний POST після мережевої помилки та розпочатий SSE не
повторюються. Інший тип 429 ставить на паузу відповідний маршрут і повертає
відмову без повтору поточного запиту. Реєстрації зберігаються; таймери
WARP скидаються лише після підтвердженої зміни його вихідного IP.
401/402/403 зупиняють весь канал Zen.

### doctor

З каталогу репозиторію, коли міст уже працює:

```sh
python3 bridge.py doctor          # таблиці, RAM і час роботи
python3 bridge.py doctor --json   # повний /health для скриптів
```

Потрібен Python 3.10+. Якщо системний `python3` у macOS старіший, вкажіть
встановлений інтерпретатор, наприклад `python3.14 bridge.py doctor`.

`doctor --json` показує `zen_direct`, `zen_proxies`, `ip_observations`, `duplicate_ips`
та `ip_monitor_error`. Для direct і кожного WARP є окремі
`quota_cooldown_seconds` і `transport_cooldown_seconds`; `cooldown_seconds` —
їхній максимум. У кожного IP-спостереження є IP, остання успішна перевірка,
попередня адреса, число змін і помилка останньої спроби. Відсутність помилки
не гарантує доступної модельної квоти: монітор робить тільки GET без інференсу.

Звичайний `doctor` показує дві таблиці українською: direct і WARP 1–8,
модельні спроби/успіхи/429/транспортні помилки та окремі перевірки IP.
У таблицях є підсумки; над ними — початок обліку й стан збереження статистики.
Колонка `RAM, МіБ` — поточне споживання контейнера WARP разом із проксі,
отримане з Docker під час запуску `doctor`. Підсумок не включає спільні витрати
Colima. `н/д` означає відсутній вимір; `+` після суми — відомо лише частину
вимірів. Для direct стоїть тире: окремого WARP-контейнера в нього немає.
Колонка `Час роботи` показує дні, години й хвилини від останнього запуску
кожного контейнера (`State.StartedAt` у Docker). Це не вік реєстрації чи час
безперервно справного тунелю. Перезапуск контейнера починає цей відлік заново,
але не скидає накопичувальну статистику. Невідомий час позначається `н/д`.
Номери вузлів зіставляються з реальними опублікованими портами контейнерів,
тому перестановка адрес у пулі не переплутує пам'ять. На macOS без явного
`DOCKER_CONTEXT`/`DOCKER_HOST` використовується контекст `colima`, як у лаунчері.
Вимірювання лише читає Docker; має обмежений час очікування й не заважає
модельним запитам. Недоступний Docker залишає таблицю читабельною з `н/д`.
`doctor --json` повертає саме `/health`, без локального опитування Docker.
Позначка «Без паузи» означає відсутність відомого cooldown, а не живу перевірку квоти.

`doctor --json` повертає повну JSON-діагностику. Поле `zen_stats` показує сумарний
облік Zen за кожним маршрутом від `started_at`:

| Поле в `routes[адреса].inference` | Що рахується |
|---|---|
| `attempts` | Кожен початок реального модельного звернення, включно зі спробою з'єднання. Локальна відмова через cooldown не рахується. |
| `successes` | Повністю завершений SSE без помилки upstream чи compatibility guard. HTTP 200 сам по собі не є успіхом. |
| `http_429` | Кожна отримана модельна HTTP-відповідь 429; автоматичний fallback рахує кожен використаний маршрут окремо. |
| `transport_errors` | Помилки з'єднання, TLS, timeout, розбору чи цілісності потоку. Скасування клієнтом та звичайний HTTP 5xx сюди не входять. |

Окремий блок `routes[адреса].ip_checks` містить `attempts`, `successes`, `errors`
для GET trace. Go, завантаження каталогу й читання `doctor` не збільшують ці
лічильники. Чотири модельні поля не є взаємовиключним повним поділом усіх
результатів: наприклад, звичайні HTTP 403/503 не є транспортними помилками.

`zen-stats.json` оновлюється атомарно після кожної зміни, права 0600. Історія
прив'язана до адреси проксі, тому додавання й перестановка слотів, зміна IP,
reset квоти та перезапуск її не скидають. Відлік починається з установлення
1.8.0; старі запити не домислюються. `persistence_error: null` означає успішне
збереження. При помилці диска лічильники продовжують рости в пам'яті й будуть
записані наступним успішним оновленням; помилку видно в `doctor`. Зламаний
збережений файл блокує запуск замість мовчазного обнулення.

`X-OMP-Zen-Route: direct|warp` показує маршрут відповіді; для WARP також є
номер `X-OMP-Zen-Proxy`. Паузи зберігаються в приватному `zen-cooldowns.json`,
історія адрес — у `zen-ips.json`. У файлі пауз також зберігається `ips` —
останній підтверджений IP кожного WARP. Перезапуск і перестановка слотів
зберігають відомі паузи; підтверджений новий IP скидає паузи лише цього WARP.

### Перезапуск WARP

Усі вісім контейнерів працюють одночасно. Зручний момент для обслуговування —
маршрут на паузі й усі його активні запити вже завершилися. Перезапуск розриває
поточні з'єднання цього контейнера. RAM і час роботи порівнюйте через `doctor`
до й після обслуговування; автоматичного перезапуску за RAM чи часом у мосту немає.

Відповідність для стандартного `deploy/zen-proxies.json`:

| WARP | Сервіс Compose | Контейнер | Локальний порт |
|---|---|---|---:|
| 1 | `warp-a` | `omp-warp-warp-a-1` | 18090 |
| 2 | `warp-b` | `omp-warp-warp-b-1` | 18091 |
| 3 | `warp-c` | `omp-warp-warp-c-1` | 18092 |
| 4 | `warp-d` | `omp-warp-warp-d-1` | 18093 |
| 5 | `warp-e` | `omp-warp-warp-e-1` | 18094 |
| 6 | `warp-f` | `omp-warp-warp-f-1` | 18095 |
| 7 | `warp-g` | `omp-warp-warp-g-1` | 18096 |
| 8 | `warp-h` | `omp-warp-warp-h-1` | 18097 |

Якщо переставляли адреси у власному пулі, звірте номер з `zen_proxies[].endpoint`
у `doctor --json`. Наступні команди виконуються з каталогу репозиторію на
macOS із Colima; на Linux із поточним Docker engine приберіть `--context colima`.

Один вузол, кілька обраних або весь пул:

```sh
# Лише WARP 3
docker --context colima compose -f deploy/warp/compose.yaml restart warp-c

# Лише WARP 3 і 4
docker --context colima compose -f deploy/warp/compose.yaml restart warp-c warp-d

# Усі вісім WARP
docker --context colima compose -f deploy/warp/compose.yaml restart
```

Це [стандартна команда Compose](https://docs.docker.com/reference/cli/docker/compose/restart/).
Вона зберігає volumes реєстрацій і не перезапускає міст. Для кількох сервісів
вузли можуть перезапускатися одночасно; завершення команди не підтверджує
готовність тунелів. Перевірка WARP 3 через його проксі:

```sh
curl --noproxy '' --proxy http://127.0.0.1:18092 --max-time 15 -fsS \
  https://opencode.ai/cdn-cgi/trace
```

Очікуйте валідний `ip=…` і `warp=on` або `warp=plus`, як у
[перевірці Cloudflare](https://developers.cloudflare.com/warp-client/get-started/linux/).
Для одного контейнера з будь-якого каталогу також працює:

```sh
docker --context colima restart omp-warp-warp-c-1
```

**Усі WARP по черзі з очікуванням готовності.** Наступний Bash-сценарій не
починає наступний перезапуск до успішного trace попереднього. Для обраних
вузлів замініть список після `for node in` на, наприклад, `warp-c warp-d`.
На Linux використайте `docker_cli=(docker)`. Перед виконанням дочекайтеся
завершення активних запитів: сценарій їх не відстежує.

```bash
(
  set -eu
  docker_cli=(docker --context colima)
  compose_file=deploy/warp/compose.yaml

  for node in warp-a warp-b warp-c warp-d warp-e warp-f warp-g warp-h; do
    "${docker_cli[@]}" compose -f "$compose_file" restart "$node"
    proxy=$("${docker_cli[@]}" compose -f "$compose_file" port "$node" 8888)
    ready=0
    for attempt in {1..15}; do
      trace=$(curl --noproxy '' --proxy "http://$proxy" --connect-timeout 2 \
        --max-time 5 -fsS https://opencode.ai/cdn-cgi/trace 2>/dev/null) || trace=
      if printf '%s\n' "$trace" | grep -Eq '^warp=(on|plus)$'; then
        printf '%s: тунель готовий\n' "$node"
        ready=1
        break
      fi
      sleep 1
    done
    if [ "$ready" -ne 1 ]; then
      printf '%s: тунель не готовий; перезапуск решти зупинено\n' "$node" >&2
      exit 1
    fi
  done
)
```

IP після перезапуску може змінитися. Щохвилинний монітор перевіряє фактичну
адресу через OpenCode: підтверджений новий IP скидає стару квотну й транспортну
паузу лише цього WARP; незмінний IP залишає їх. Перша перевірка без історії
та помилка trace нічого не скидають. Лічильники й реєстрації зберігаються.
Новий IP не гарантує доступної модельної квоти: нова 429 знову поставить
відповідний маршрут на паузу. Після обслуговування запустіть `python3 bridge.py doctor`.

Міст перезапускайте після змін серверного коду/параметрів запуску або при
його зависанні (див. [оновлення](#10-оновлення-і-видалення)). Для WARP підстави —
несправний тунель, повторні транспортні помилки або зростання RAM, яке створює
тиск на систему. Самі 300 МіБ не доводять витік і не є встановленим лімітом WARP.

Зупинити всі вузли зі збереженням реєстрацій:

```sh
docker --context colima compose -f deploy/warp/compose.yaml stop
```

### Автозапуск (systemd, Linux)

```sh
mkdir -p ~/.config/systemd/user
cp deploy/omp-free-bridge.service ~/.config/systemd/user/
systemctl --user daemon-reload
systemctl --user enable --now omp-free-bridge
python3 bridge.py doctor
```

Юніт очікує код у `~/.local/share/omp-free-bridge`; якщо клонували в інше
місце — виправте `WorkingDirectory` і `ExecStart`. Щоб міст працював і без
відкритої сесії користувача: `sudo loginctl enable-linger $USER`.
Збережений `zen-proxies.json` читається і в systemd. Щоб піднімати контейнери
разом із мостом, замініть `ExecStart` на `/bin/bash %h/.local/share/omp-free-bridge/deploy/start-warp.sh --port 8765 --compat-opencode`.

### Автозапуск (macOS, launchd)

Використовуйте один LaunchAgent для моста: лаунчер сам запускає Colima й
наявні контейнери. Для вже налаштованого агента достатньо змінити команду
запуску, зберігши решту ваших параметрів. Приклад нового
`~/Library/LaunchAgents/local.omp-bridge.plist`:

```xml
<?xml version="1.0" encoding="UTF-8"?>
<plist version="1.0"><dict>
  <key>Label</key><string>local.omp-bridge</string>
  <key>ProgramArguments</key><array>
    <string>/bin/bash</string>
    <string>/Users/YOUR_USER/.local/share/omp-free-bridge/deploy/start-warp.sh</string>
    <string>--compat-opencode</string>
  </array>
  <key>EnvironmentVariables</key><dict>
    <key>PATH</key><string>/opt/homebrew/bin:/usr/local/bin:/usr/bin:/bin:/usr/sbin:/sbin</string>
    <key>OMP_FREE_PYTHON</key><string>/opt/homebrew/bin/python3.14</string>
  </dict>
  <key>RunAtLoad</key><true/>
  <key>StandardOutPath</key><string>/Users/YOUR_USER/.config/omp-free-bridge/logs/server.log</string>
  <key>StandardErrorPath</key><string>/Users/YOUR_USER/.config/omp-free-bridge/logs/server-error.log</string>
</dict></plist>
```

Замініть `YOUR_USER`, шлях до репозиторію та інтерпретатора на свої абсолютні
шляхи (Python 3.10+). `launchd` не розгортає `~` у plist. Створіть теку логів
і завантажте новий агент:

```sh
mkdir -p ~/.config/omp-free-bridge/logs
launchctl bootstrap gui/$(id -u) "$HOME/Library/LaunchAgents/local.omp-bridge.plist"
python3 bridge.py doctor
```

`doctor` має показати direct і вісім WARP у таблицях; `doctor --json` —
`zen_proxy: true` і вісім записів `zen_proxies`.
Це перевірка налаштування; доступність IPv6 перевіряється GET trace вище.

## 4. Підключення до OMP

Міст має бути запущений **до** старту OMP: розширення при завантаженні читає
локальний токен і каталог.

**Разово**, для однієї сесії:

```sh
omp -e ~/.local/share/omp-free-bridge/extension.mjs \
  --model opencode-zen-free/big-pickle
```

**Назавжди** — посилання в теку автоматичного пошуку розширень. Ім'я файлу
має закінчуватися на `.js` (явний `-e` приймає і `.mjs`):

```sh
mkdir -p ~/.omp/agent/extensions
ln -sf ~/.local/share/omp-free-bridge/extension.mjs ~/.omp/agent/extensions/omp-bridge.js
omp models opencode-zen-free
```

Після цього `opencode-zen-free/…` і `opencode-go-free/…` з'являються в
`/model`, у `--model`, у ролях `--smol`/`--slow`/`--plan` і для підагентів.

## 5. Вибір моделі

- Два провайдери: `opencode-zen-free` і `opencode-go-free`. Модель з тим самим
  ID в обох — два різні вибори, міст ніколи не перекидає запит з одного на
  інший.
- ID беруться з живого каталогу, тому список змінюється разом з OpenCode.
  Подивитися поточний: `/free-models` в OMP, `omp models opencode-zen-free`
  або `python3 bridge.py catalog`.
- У меню OMP моделі підписані `[ZEN FREE] …` і `[GO FREE] …`.
- Старі сесії з провайдером `opencode-free/…` (до 1.3.0) після відновлення
  отримають 404 з підказкою. Виберіть модель заново.

## 6. OpenCode Go

```sh
python3 bridge.py login            # ключ вводиться приховано, файл 0600
systemctl --user restart omp-free-bridge   # або перезапустіть serve вручну
```

Замість файлу можна передати ключ змінною `OPENCODE_API_KEY` у середовище
процесу `serve`. Токени Console (`st-…`) — не API-ключі, міст їх відхиляє.
Go-провайдер з'явиться, лише якщо в каталозі Go знайдеться модель із
підтвердженою нульовою ціною; включена в підписку модель — це не «free».

## 7. Команди

**В OMP** (додає розширення):

| Команда | Що робить |
|---|---|
| `/free-models` | Пропущені маршрути `lane/id — протокол` і скільки відкинуто |
| `/free-refresh` | Перечитати каталог моста й оновити список моделей без рестарту OMP |

**`bridge.py`**:

| Команда | Що робить |
|---|---|
| `login` | Зберегти ключ Go у `zen.key` (0600). Мережі не торкається. |
| `catalog` | Зібрати й показати каталог. Без інференсу. |
| `serve` | Запустити міст (див. розділ 3). |
| `doctor` | Запитати `/health` і показати читабельні таблиці статистики та стану. Без інференсу. |
| `doctor --json` | Повернути повну JSON-відповідь `/health` для скриптів. |
| `probe --model ID [--lane zen\|go]` | Один справжній запит «відповідай BRIDGE_OK» до моделі. |
| `probe --all` | По одному запиту на кожну модель, зупиняється на першій відмові квоти чи політики. |

`probe` витрачає free-квоту. Успіх — тільки `MODEL_ANSWER_CONFIRMED`, тобто
завершена відповідь з точним текстом. 429 — це `QUOTA_LIMIT_NOT_SUCCESS`, не
«майже працює».

## 8. Файли стану і змінні

Усе лежить у `~/.config/omp-free-bridge` (або в `$OMP_FREE_HOME`), права 0600:

| Файл | Що це |
|---|---|
| `local.token` | Випадковий токен між OMP і мостом. Створюється сам. Не ключ OpenCode. |
| `runtime.json` | Порт і PID запущеного моста. Звідси розширення знає, куди стукати. |
| `zen-proxies.json` | Запасний пул із 1–8 адрес HTTP CONNECT-проксі; `serve` читає при старті. Zen завжди починає напряму. |
| `zen-ips.json` | Останні перевірені IP, попередні адреси, лічильники змін і помилки перевірки. |
| `zen-stats.json` | Постійні лічильники модельних запитів і окремих перевірок IP за адресами маршрутів. |
| `zen-cooldowns.json` | Паузи прямої free-квоти та WARP-виходів за адресами; переживають перезапуск. |
| `catalog.json` | Останній каталог — звіт для людини й імена моделей на час збою. Для дозволу на запит не використовується. |
| `zen.key` | Ключ Go після `login`. |
| `probe-results.json` | Результати останнього `probe`. |

| Змінна | Що робить |
|---|---|
| `OMP_FREE_HOME` | Інша тека стану (і для моста, і для розширення). |
| `OPENCODE_API_KEY` | Ключ Go без файлу `zen.key`. |
| `OMP_FREE_PYTHON` | Інтерпретатор для `deploy/start-warp.sh`; за замовчуванням `python3`. |

## 9. Коли щось пішло не так

Міст завжди відповідає помилкою з кодом, а не мовчить і не підставляє іншу
модель. Код видно в повідомленні OMP.

| Код / статус | Що сталося | Що робити |
|---|---|---|
| `Спочатку запустіть: python3 bridge.py serve…` | OMP стартував раніше за міст | Запустіть міст, потім OMP |
| `401 Invalid local proxy token` | Токен у OMP і в мосту різні | Перезапустіть OMP після перезапуску моста з іншим `OMP_FREE_HOME` |
| `403 PaidOrUnknownModelBlocked` | Моделі немає в поточному free-каталозі | `/free-models`; можливо, модель стала платною або зникла |
| `403 FreeTierError` (від OpenCode) | Шлюз не прийняв форму запиту | Перевірте, що `serve` запущено з `--compat-opencode`; якщо так — шлюз змінив правила |
| `503 ZenProxyCooldown` після квотних відмов | Усі налаштовані маршрути Zen на паузі | Чекати до найближчого reset; відмова одного маршруту автоматично пробує наступний |
| `409 FreeQuotaCooldown` | Пауза квоти Go | Чекати до reset Go |
| `409 LocalCooldown` | Пауза після 429 ще йде | Чекати; запит до OpenCode навіть не надсилався |
| `503 ZenProxyCooldown` | Усі налаштовані виходи на паузі | Чекати до вказаного часу; стан кожного — у `doctor` |
| `409 UpstreamLaneStopped` | OpenCode відповів 401/402/403, канал зупинено | Розібратися з причиною (ключ, підписка, акаунт), потім перезапустити міст |
| `401 GoCredentialsMissing` | Go без ключа | `python3 bridge.py login` |
| `409 BridgeStubToolError` | Модель спробувала викликати інструмент-заглушку | Дайте OMP повний набір інструментів (не обрізайте `--tools` до одного-двох) |
| `502 TruncatedStream` | Потік обірвався без фінальної події | Повторіть запит; відповідь не вважається завершеною |
| `502 BridgeTransportError` | Проксі або upstream-з'єднання не спрацювало | Перевірте вузли; проблемний на паузі, наступне звернення використає інший доступний |
| `Cannot read zen-proxies.json` | Файл пулу недоступний або зламаний | Виправте файл перед запуском; прямий fallback не вмикається |
| `400 StreamingRequired` | Клієнт попросив не-потокову відповідь | Звичайний OMP завжди стрімить; це сторонній клієнт |
| `503 CatalogUnavailable` | Не вдалося перевірити каталог | Мережа або OpenCode недоступні; старий каталог для дозволу не використовується |
| `404 RouteRemoved` | Стара модель `opencode-free/…` | Виберіть `opencode-zen-free/…` або `opencode-go-free/…` |

Не ставте автоматичний рестарт моста, щоб «скинути» 429 або 403: обмеження
акаунта від цього не зникає, а повторні спроби можуть зашкодити акаунту.

## 10. Оновлення і видалення

```sh
cd ~/.local/share/omp-free-bridge
git pull --ff-only
python3 -m unittest -q tests/test_bridge.py
node --test tests/extension.test.mjs
```

Перезапустіть міст відповідно до способу запуску:

- Linux/systemd: `systemctl --user restart omp-free-bridge`.
- macOS/launchd: `launchctl kickstart -k gui/$(id -u)/local.omp-bridge`.
- У терміналі: зупиніть поточний процес і повторіть свою команду запуску.

Після зміни самого plist треба вивантажити агент через `launchctl bootout`,
дочекатися його завершення та знову виконати `bootstrap`. Для оновлення коду
за незмінного plist достатньо `kickstart`. Потім у відкритих сесіях OMP — `/free-refresh`.

Якщо змінилися файли `deploy/warp`, перебудуйте image та оновіть контейнери:

```sh
docker build -t omp-bridge-warp:local deploy/warp
docker compose -f deploy/warp/compose.yaml up -d --no-build
```

Для Colima використовуйте контекст `colima`, як при встановленні. Volumes
зберігаються; повторно виконувати `registration new` не треба. IP можуть змінитися.
Рестарт моста зберігає квотні й транспортні паузи Zen у `zen-cooldowns.json`;
оновлення коду не скидає відомих квотних дедлайнів.

Перед видаленням зупиніть свій автозапуск командою для своєї ОС:

- Linux: `systemctl --user disable --now omp-free-bridge`.
- macOS: `launchctl bootout gui/$(id -u)/local.omp-bridge`.

Якщо користувалися WARP, приберіть контейнери до видалення репозиторію:

```sh
docker compose -f deploy/warp/compose.yaml down
```

Без `-v` реєстрації у volumes залишаються. Приберіть свій systemd unit або
LaunchAgent, посилання на розширення та файли моста:

```sh
rm ~/.omp/agent/extensions/omp-bridge.js
rm -r ~/.local/share/omp-free-bridge ~/.config/omp-free-bridge
```

## 11. Перед тим як надсилати свій код

Безкоштовні моделі OpenCode — не приватний інференс. Частина free і
contributor-моделей може використовувати дані для навчання
([Zen Privacy](https://opencode.ai/docs/zen/#privacy)). Міст не анонімізує
запити. Не надсилайте ключі, паролі, персональні дані й код, на який у вас
немає дозволу.
